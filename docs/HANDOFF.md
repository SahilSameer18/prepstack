## 2. Rules that cost the owner time when broken
- **Git:** never stage, commit or push. Give the `git add` and a one-line `git commit -m "..."` (no trailer, no Co-Authored-By). Never touch `server/.env`. Never use ports 3000 or 5173 for throwaway servers (use 3100 for the server and 5175 for the client; start the client with `VITE_API_URL=http://localhost:3100`).
- **The owner decides.** Recommend first, then ask. Do not record your own pick as decided. The owner works in short messages ("lets do next phase"): do the work, then report.
- **Cost matters** to the owner: prefer scripts and tests over many sub-agents; reply briefly.
- **Learner-facing text is in easy words** a non-technical person can follow: keep the technical term, add its plain meaning at first use. No "master/slave". PrepStack is **free**; login is only the gate for saving and generating.
- **Notes and content** (only if you touch them): every fact from a primary source that was actually read; numbers from scripts in `docs/content/checks/`; own words; claims in `docs/content/SOURCES.md`; reviewers re-fetch sources; publish only on the owner's word. Rules: `docs/content/NOTES_TEMPLATE.md`.
- **Tests with every change; mutation checks** on rules that matter (ownership, limits, money-like rules): break the code on purpose, see a test fail, restore. Say what was not checked.
- **The Today screen is sacred** (decision 33): only today's items, the time needed and one big Start button. Nothing may be added without the owner's say-so, and a client test must fail if it shows more.

## 3. My plan: the API a client can call (all under `/api/plan`, JSON, `{ success, message, data }`)
Public: `POST /preview` body = the form (below). Login (cookie session, same as the rest of the app): `GET /` , `POST /`, `DELETE /`, `DELETE /history`, `POST /changes/preview`, `POST /changes/apply`, `GET /review?weekStart=YYYY-MM-DD`, `POST /items`, `PATCH /items/:id`, `DELETE /items/:id`, `PATCH /items/:id/star`, `POST /items/:id/result`, `POST /items/:id/review`, `POST /items/:id/skip`, `POST /items/:id/unskip`.
- **The form** (`validators/plan.validators.js`): `goalType` placements | role | bigtech; `style` one-topic | mixed; `weeks` 1 to 52; `weekdayHours` and `weekendHours` (0 or 0.5 to 12); `restDay` null or 0 (Monday) to 6 (Sunday); `startDate` optional (default today in India; from yesterday to 60 days ahead); `sheetSlug` (placements and bigtech; bigtech allows only `neetcode-150` or `striver-sde`); `roadmapSlug` (role); `subjects` from os, dbms, cn, oops, hld; `knownTopics` topic ids. `POST /` also takes `title`, `targetRole`, `replace`.
- **Preview answer:** `{ startDate, deadline, finishDate, earlyDays, notices[], coverage { syllabusMinutes, plannedMinutes, extraMinutes, leftOutCount, leftOutMinutes, alreadySolved }, week1 { week, from, to, minutes, items[] } }`. Notices: `planned-85`, `core-first`, `core-does-not-fit`, `early-finish`, `nothing-to-plan`. Only week 1 is ever sent to a logged-out visitor.
- **`GET /`** gives `{ plan, today, finished }`. `plan` has the settings, `coverage` (with `leftOut[]`), `notices` and `items[]` (`id`, `key`, `type`, `ref`, `link`, `title`, `plannedMinutes`, `day`, `part`, `core`, `starred`, `locked`, `skipped`, `result`, `doneAt`, `nextReviewDay`, `solvedOnSheet`, ...). `today` is `{ date, isToday, items[], minutes, startItem, onTrack { status, daysBehind, missedItems, suggestRebuild, text } }`: **the Today screen shows only this** (carried-over items first, then today's, then due reviews; a review item has `originalKey` and its original item's `id` is the one to send to `/review`). Treat `solvedOnSheet: true` as done.
- **Changes:** `POST /changes/preview` body `{ type: rebuild | hours | lighter, weekdayHours?, weekendHours?, restDay?, lighterDays?[{from,to,hours}] }` returns `{ diff { finishText, movedItems, newlyLeftOut, doneProtected, lockedKept, checksum, ... }, plannedMinutes, leftOutCount, finishDate }` and saves nothing; `/changes/apply` takes the same body plus `checksum` and refuses (409) if anything changed. Always preview, show the diff, then apply.
- **Ticking:** `PATCH /items/:id { done: true, result? }` or `POST /items/:id/result { result: alone | hints | solution }` (a notes section sends `{ quizScore: 0..5 }`); the three buttons "Solved alone", "With hints", "Needed the solution" call `/result`. A DSA tick also marks the problem solved on its sheet. `PATCH /items/:id { day }` moves (at most 3 days, locks). `DELETE` only removes items the student added; an item from the plan is skipped instead.
- **Limits** (`server/src/config/limits.js`): preview 20 a minute per IP; 10 saved plans an hour; 20 changes a minute; 60 ticks a minute; 600 items per plan.

## 4. How the client is built (read these before Phase 5)
- React 19 + Vite + Tailwind, tokens only (`client/src/index.css`); a test (`client/src/test/colorGuard.test.js`) fails on a raw hex, rgb or Tailwind palette colour. Shared states in `client/src/components/ui/StateComponents.jsx` (`EmptyState`, `LimitState`, `PageErrorState`, `UsageNotice`). API calls in `client/src/api/services/*` (see `notesService`, `dsaSheet` for the pattern; the Axios instance refreshes tokens). Routes in `client/src/router`. The dashboard's existing checklist is `client/src/components/analyzer/PlanChecklist.jsx` and `TodayCard.jsx` (reuse, never copy). A public page needs an entry in `client/src/seo/pages.js` and the prerender/`seo-check` count (`npm run build` prints it; the description must be 160 characters or fewer).

## 5. Practical notes that save time
- Windows + Git Bash; Python is `python` (3.13). Write scripts to files instead of long shell one-liners (quoting breaks). Edit files with exact-string replacement and run the tests after each change.
- Server tests use an in-memory MongoDB (`server/test/helpers/setup.js`); `planClock.now` (in `server/src/services/planData.js`) lets a test play a plan on another day. Do not run seeds against a real database; the owner runs `npm run seed:notes` and `npm run seed:all`.
- The generator and adjust module are pure (`server/src/services/planGenerator.js`, `planAdjust.js`); change a rule only with a test and re-check the acceptance example (`server/test/plan-generator.test.js`, numbers pinned for 12, 8 and 6 weeks).
- `npm run build:plan-catalogs` (server) rebuilds `roadmapCatalog.json` and `planCatalog.json` after a roadmap or sheet-topic change; a test fails until you do.
- Keep `PROJECT_STATUS.md`, `TESTING.md`, the README test counts and the plan's status paragraph true after every phase. Write the next commit command for the owner at the end of each piece.
