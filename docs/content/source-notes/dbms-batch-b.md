### Transactions (chapter 17)
- A transaction is a unit of program execution that reads and possibly updates data items. Two things to handle: failures (hardware, crashes) and concurrent execution. Slide example: transfer $50 from A to B as read(A), A := A - 50, write(A), read(B), B := B + 50, write(B). (17.3)
- Atomicity: if the transaction fails after write(A) and before write(B), money is "lost"; the updates of a partly executed transaction must not be reflected. Durability: once the user is told the transfer is done, it must persist through failures. (17.4)
- Consistency: here, A + B is unchanged by the transaction. Consistency includes declared constraints (primary and foreign keys) and implicit ones. The database may be temporarily inconsistent during the transaction, and must be consistent when it completes successfully. Wrong transaction logic can still break consistency. (17.5)
- Isolation: if another transaction reads between write(A) and write(B), it sees A + B smaller than it should be. Running transactions one after another gives isolation trivially, but concurrency has benefits. (17.6)
- ACID definitions (17.7): atomicity (all operations are reflected or none); consistency (a transaction run alone preserves consistency); isolation (each transaction is unaware of the others; intermediate results are hidden); durability (changes persist after successful completion, even with failures).
- Transaction states: active (while executing), partially committed (after the final statement), failed (normal execution cannot continue), aborted (rolled back and the database restored; the transaction can then be restarted, only if there was no internal logical error, or killed), committed (after successful completion). (17.8)
- Why run transactions concurrently: better processor and disk use and throughput; shorter average response time because short transactions need not wait behind long ones. (17.10)
- A schedule is the time order of the instructions of concurrent transactions; it must contain all instructions of each transaction and keep each transaction's own order. A completed transaction ends with commit, a failed one with abort. (17.11)
- Slide example: T1 transfers $50 from A to B; T2 transfers 10% of A's balance to B. Serial schedules (T1 then T2, or T2 then T1) preserve A + B. A non-serial schedule can be equivalent to a serial one (schedule 3) or can fail to preserve A + B (schedule 4). (17.12 to 17.15)
- Serializable: a schedule is serializable if it is equivalent to a serial schedule; two notions of equivalence: conflict and view. The basic assumption is that each transaction on its own preserves consistency. (17.16)
- Conflicting instructions: two instructions of different transactions conflict when they access the same item and at least one writes it. Read-read does not conflict; read-write, write-read and write-write do. (17.18)
- Conflict serializable: a schedule that can be turned into a serial one by swapping adjacent non-conflicting instructions. (17.19) Example of one that is not conflict serializable: no swaps reach either serial order of T3 and T4. (17.21)
- View serializable: view equivalent to a serial schedule (same initial reads, same reads-from, same final writes). Every conflict serializable schedule is view serializable; a view serializable schedule that is not conflict serializable has blind writes. (17.22, 17.23)
- Test for conflict serializability: draw a precedence graph (a node per transaction, an arc Ti to Tj when they conflict and Ti accessed the item first). The schedule is conflict serializable if and only if the graph has no cycle; a topological order of the graph is a serial order. (17.25, 17.26) Testing view serializability is NP-complete. (17.27)
- Recoverable schedule: if Tj reads a value written by Ti, then Ti commits before Tj commits. Otherwise, if Ti aborts, Tj has read an inconsistent state. (17.28)
- Cascading rollback: one failure forces a chain of rollbacks of transactions that read uncommitted data. Cascadeless schedule: a transaction reads an item only after the transaction that last wrote it has committed. Every cascadeless schedule is recoverable. (17.29, 17.30)
- Concurrency control must ensure schedules are serializable and recoverable, preferably cascadeless. One transaction at a time gives serial schedules but poor concurrency. Testing serializability after the fact is too late, so protocols impose a discipline that avoids non-serializable schedules. (17.31 to 17.33)
- Weak consistency: some applications accept non-serializable schedules (for example an approximate total balance). SQL-92 levels as the slides list them: serializable (the standard's default), repeatable read, read committed, read uncommitted. Warning on the slides: some systems do not give serializable by default; Oracle, and PostgreSQL before version 9, default to snapshot isolation, which is not in the SQL standard. (17.34 to 17.36)
- In SQL a transaction begins implicitly and ends with COMMIT or ROLLBACK; in almost all systems each successful statement also commits implicitly unless that is turned off (for example `setAutoCommit(false)` in JDBC). The isolation level is set with `set transaction isolation level ...`. (17.37)
- Ways to implement isolation: locking, timestamps, multiple versions (snapshots). (17.38)
- Phantom with SQL: T1 selects rows with salary above 90000 using an index and locks them; T2 inserts a new row that matches; tuple locks alone miss the conflict. The idea: detect predicate conflicts. (17.39)

### Concurrency control (chapter 18)
- Lock modes: exclusive (X: read and write) and shared (S: read only). Any number of transactions can hold S on an item; if one holds X, no other transaction may hold any lock on it. A request is granted only if compatible with the locks other transactions hold. (18.3, 18.4)
- A locking protocol is a set of rules for requesting and releasing locks; protocols enforce serializability by restricting the possible schedules. (18.5)
- Deadlock: T3 waits for a lock T4 holds and T4 waits for one T3 holds; one must be rolled back. Deadlock is possible in most locking protocols. Starvation is also possible: for example an X-lock request waiting while a stream of S-lock requests keeps being granted, or the same transaction rolled back repeatedly. (18.6, 18.7)
- Two-phase locking (2PL): a growing phase (acquire locks, release none) then a shrinking phase (release locks, acquire none). It ensures conflict-serializable schedules; transactions can be serialized in the order of their lock points. It does not prevent deadlock. (18.8, 18.9)
- Strict 2PL: hold all exclusive locks until commit or abort (gives recoverability and no cascading rollbacks). Rigorous 2PL: hold all locks until commit or abort (serialization order is commit order). Most databases implement rigorous 2PL and just call it two-phase locking. (18.9)
- 2PL is not necessary for serializability: some conflict serializable schedules cannot be produced under it. (18.10)
- Lock conversions: upgrade S to X in the growing phase, downgrade X to S in the shrinking phase. (18.12) Systems usually take locks automatically: a read takes S, a write takes X (upgrading if needed), and all locks are released at commit or abort. (18.13, 18.14)
- The lock manager keeps an in-memory lock table with granted and waiting requests per item; new requests join the end of the queue and are granted if compatible with earlier ones. (18.15, 18.16)
- Deadlock prevention: lock everything before starting; or lock in a fixed order. Timestamp schemes: wait-die (older may wait for younger; younger is rolled back instead of waiting; may die several times) and wound-wait (older forces younger to roll back; younger may wait for older; fewer rollbacks). A rolled-back transaction restarts with its original timestamp, so older ones have priority and starvation is avoided. (18.21, 18.22) Timeout schemes: simple, but may roll back without a deadlock, and picking the timeout is hard. (18.23)
- Deadlock detection: build a wait-for graph (transactions as nodes, an edge Ti to Tj when Ti waits for a lock held by Tj in a conflicting mode); there is a deadlock if and only if the graph has a cycle. Run the check periodically. Recovery: pick a victim with minimum cost; total or partial rollback; to avoid starvation never pick the oldest transaction as the victim. (18.24, 18.25)
- Multiple granularity: lock at different sizes (database, area, file, record). Fine granularity gives more concurrency but more locking overhead; coarse granularity the opposite. Intention modes IS, IX and SIX let a transaction lock a higher node without checking all descendants; locks are taken root to leaf and released leaf to root. Lock escalation switches to a coarser lock when there are too many fine ones. (18.26 to 18.30)
- Phantom phenomenon: T1 reads all Physics instructors, T2 inserts a Physics instructor; they conflict without touching a common tuple; tuple locks alone allow non-serializable results. Second example: two transactions both read the maximum ID and create ID + 1, so both get the same ID. Solutions: lock a data item that represents the relation's contents (low concurrency for inserts) or index locking: lock the index leaf nodes a lookup touches, even if no row matches, and insert/delete takes X locks on the affected leaves. (18.32 to 18.35)
- Timestamp ordering is an alternative to locking: each item stores a read and a write timestamp to detect out-of-order access. (17.38, 18.45)
- Multiversion schemes: every write creates a new version; a read picks the right version for its timestamp, so reads never wait. Costs: extra storage and per-tuple version info; old versions can be garbage collected once no active transaction needs them; trouble with key constraint checking and indexes on versioned rows. (18.52 to 18.59)
- Snapshot isolation: a transaction reads and writes in its own snapshot of committed data taken at the start; other transactions' updates are invisible; first committer wins (a transaction commits only if no concurrent transaction already wrote the item it wants to write). Benefits: reads never block and are not blocked; performance similar to read committed; no dirty reads, lost updates or non-repeatable reads. (18.60 to 18.64)
- Snapshot isolation is not always serializable: **write skew**, where two concurrent transactions each modify a different item based on a state the other changes, can violate integrity constraints; inserts can show the same effect (two transactions both read the maximum order number and create the same new number, a phantom case). The slides say it is not very common in practice but developers should be careful. Using snapshots to check key and foreign key integrity can be inconsistent, so such checks are done outside the snapshot. (18.64 to 18.66)
- Serializable snapshot isolation (SSI) also tracks read-write dependencies and rolls back transactions that would form a cycle, giving serializability; implemented in PostgreSQL from version 9.1; the PostgreSQL version also uses index locking to catch phantoms. (18.67)

## S2b. PostgreSQL 18 documentation (read 10 Nov 2026)

Pages: `.../docs/current/mvcc-intro.html` (13.1), `.../transaction-iso.html` (13.2), `.../explicit-locking.html` (13.3, deadlocks and row-level locks). Version 18; no date on the pages; copyright 1996-2026 PostgreSQL Global Development Group; permissive licence (batch A S2).

- MVCC: each statement sees a snapshot of the data as of some earlier moment, whatever other transactions are doing; reads and writes do not block each other, even at Serializable (which uses serializable snapshot isolation). The page says MVCC generally performs better than locking and minimizes lock contention. Table and row locks and application-level advisory locks exist for explicit control. (13.1)
- Isolation: the page defines four phenomena: dirty read, nonrepeatable read, phantom read and serialization anomaly. Table 13.1 as PostgreSQL states it: Read uncommitted (dirty read "allowed, but not in PG"; the rest possible); Read committed (dirty read not possible; nonrepeatable, phantom and serialization anomaly possible); Repeatable read (dirty and nonrepeatable not possible; phantom "allowed, but not in PG"; serialization anomaly possible); Serializable (none possible). (13.2)
- **Default is Read Committed.** PostgreSQL accepts all four SQL levels but implements three: its Read Uncommitted behaves like Read Committed. (13.2)
- Read Committed: each statement sees data committed before that statement began. An UPDATE that meets a row changed by a concurrent transaction waits for it; if it commits, the WHERE condition is re-checked against the new row version. Page example: `UPDATE website SET hits = hits + 1` in one session and `DELETE ... WHERE hits = 10` in another on a row that moves from 9 to 11: the delete finds nothing. (13.2)
- Repeatable Read: the snapshot is taken at the first non-transaction-control statement; if a concurrent transaction committed an update to a row this one wants to change, it fails with "could not serialize access due to concurrent update" and the application must retry. The page calls this level snapshot isolation and says it still allows serialization anomalies (a control-record and batch-detail example); read-only transactions never get serialization conflicts. (13.2)
- Serializable: uses predicate locks that never block and cannot cause deadlock; they only flag dependencies. Page example: table with (class, value) rows (1,10), (1,20), (2,100), (2,200); T A sums class 1 (30) and inserts 30 as a class 2 row; T B sums class 2 (300) and inserts 300 as a class 1 row. Under Repeatable Read both commit; under Serializable one fails. Failures use SQLSTATE 40001 and the application must retry. (13.2)
- Deadlock: two transactions each hold a lock the other wants (T1 locks A then wants B; T2 locks B then wants A; a row example with two accounts). PostgreSQL detects it and aborts one; which one is hard to predict. Advice: lock in a consistent order, take the strictest lock first, retry aborted transactions. Without a detected deadlock a waiting transaction waits indefinitely. (13.3.4)
- Row-level locks block only writers and lockers, not plain SELECTs: FOR UPDATE (blocks UPDATE, DELETE and all FOR variants; DELETE takes it), FOR NO KEY UPDATE (weaker; taken by an UPDATE that does not change key columns), FOR SHARE, FOR KEY SHARE (weakest). (13.3.2)

## S8b. MySQL 8.4 Reference Manual (read 10 Nov 2026)

Pages: isolation levels (17.7.2.1), InnoDB multi-versioning (17.3), InnoDB deadlocks (17.7.5), InnoDB locking (17.7.1). Manual version 8.4; no dates; "(c) 2026 Oracle"; no reuse licence stated (batch A S8).

- Default isolation level for InnoDB is REPEATABLE READ. READ UNCOMMITTED: plain SELECTs run without locks and may read earlier row versions (dirty reads). READ COMMITTED: each consistent read sets its own fresh snapshot; gap locking is disabled, so phantom rows can occur. REPEATABLE READ: consistent reads within a transaction use the snapshot of the first read. SERIALIZABLE: like repeatable read, but with autocommit off plain SELECTs become SELECT ... FOR SHARE. InnoDB offers all four SQL:1992 levels. (17.7.2.1)
- InnoDB keeps old row versions in undo logs; each row has hidden fields: the last transaction id that changed it (DB_TRX_ID), a roll pointer to the undo record (DB_ROLL_PTR) and a row id. A delete is an update that sets a deleted bit; a purge removes the row later. Commit regularly, including read-only transactions, or the rollback segment can grow. (17.3)
- Deadlocks: transactions each hold a lock another needs. Common causes: locking rows of several tables in opposite orders, or ranges and gaps with different timing. Reduce them by keeping transactions small and short, using the same order of operations, and indexing the columns used in SELECT ... FOR UPDATE and UPDATE ... WHERE. The isolation level does not change the possibility of deadlock, because deadlocks come from writes. Detection is on by default; InnoDB rolls back one transaction (the victim); the application must handle retries. If detection is turned off, `innodb_lock_wait_timeout` ends the wait. (17.7.5)
- Record lock: a lock on an index record. Gap lock: a lock on the gap between index records, blocking inserts into it; gap locks do not conflict with each other; disabled under READ COMMITTED except for foreign key and duplicate key checks. Next-key lock: a record lock plus a gap lock on the gap before the record; under the default REPEATABLE READ, InnoDB uses next-key locks for searches and index scans, which prevents phantom rows. Example: an index with 10, 11, 13, 20 has next-key intervals (-infinity,10], (10,11], (11,13], (13,20], (20,+infinity). (17.7.1)

## S7b. Wikipedia (read 10 Nov 2026; CC BY-SA 4.0, "additional terms may apply")

Pages: ACID (edited 24 Oct 2026), Isolation (database systems) (15 Oct 2026), Database transaction schedule (7 Sep 2026), Two-phase locking (3 May 2026). Used for coverage and to cross-check S1b and S2b, not as the only source of a disputable claim.

- ACID: the acronym was coined by Reuter and Härder in 1983; the page ties atomicity to write-ahead logging and shadow paging; isolation is the main goal of concurrency control; durability usually means recorded in non-volatile memory. Distributed atomicity uses two-phase commit, which the page says is not the same as two-phase locking. The page says ACID databases prioritize consistency over availability.
- Isolation: three read phenomena as in SQL-92: dirty read (reading an uncommitted change), non-repeatable read (re-reading a row that another transaction changed and committed), phantom read (re-running a query whose row set changed because of committed inserts or deletes). Levels as the standard describes: serializable prevents all three; repeatable read allows phantoms only; read committed allows non-repeatable and phantom reads; read uncommitted allows all three. The page says default levels vary quite widely across products, that the ANSI definitions are called ambiguous and not a good match for many real systems (which mostly use locking), and that write skew can occur at repeatable read in some systems.
- Schedules: serial, serializable, conflict serializable (precedence graph without a cycle), view serializable (every conflict serializable schedule is view serializable, not the reverse; checking it is NP-complete), recoverable, cascadeless, strict. Containment: serial is inside conflict serializable, which is inside view serializable; serial is inside strict, inside cascadeless, inside recoverable. The page says most general-purpose databases use conflict serializable and strict recoverable schedules.
- Two-phase locking: guarantees conflict serializability; expanding then shrinking phase; shared and exclusive locks; can deadlock. Conservative 2PL takes every lock before the transaction starts and so avoids deadlock, but needs the read and write sets up front and is rarely used. Strict 2PL holds write locks until the end (gives strictness); strong strict (rigorous) 2PL holds all locks until commit or abort.

## Differences between sources the notes must not hide

1. **Default isolation level.** SQL-92 as the textbook slides describe it lists serializable as the default. PostgreSQL's default is Read Committed (S2b) and MySQL InnoDB's is REPEATABLE READ (S8b). So "the default isolation level" has no single answer: always name the database. (S1b 17.35, 17.36; S2b; S8b)
2. **Repeatable Read and phantoms.** The standard allows phantoms at repeatable read (S7b, S1b 17.35). PostgreSQL's repeatable read does not allow them (S2b table "allowed, but not in PG"). InnoDB uses next-key locks under repeatable read, which prevents phantom rows for locking reads (S8b). So "repeatable read allows phantoms" is true for the standard, not for PostgreSQL.
3. **Read Uncommitted.** PostgreSQL treats it as Read Committed, so dirty reads never happen there (S2b); MySQL InnoDB does allow them (S8b).
4. **Locks versus versions.** PostgreSQL and InnoDB read from versions (MVCC) and do not take read locks for plain SELECTs; textbook 2PL describes read locks (S1b 18.3, S2b 13.1, S8b). The notes should teach 2PL as the theory and say that real systems combine it with versions.
