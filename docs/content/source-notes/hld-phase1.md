## 2. SRE book facts we may restate (chapter, section)
- **Ch. 4:** SLI, SLO, SLA defined; an SLA has a consequence, otherwise it is an SLO; error budget as "an SLO for meeting other SLOs"; use percentiles because averages hide the tail (example 50 ms typical, 5% twenty times slower); targets: do not pick from current performance, few SLOs, loose first; Google Compute Engine's published target 99.95% ("three and a half nines").
- **Ch. 6:** four golden signals (latency, traffic, errors, saturation); a slow error is worse than a fast error; symptoms vs causes; black-box vs white-box; saturation: latency rises first, so use the 99th percentile over a short window.
- **Ch. 19:** DNS balancing limits (little control, caching, 512-byte reply limit); virtual IP; hashing packets mod N remaps nearly all connections when N changes, consistent hashing reduces that.
- **Ch. 20:** lame duck state (a task still serving but asking clients to stop sending), shutdown interval 10 to 150 s; subset size 20 to 100 backends; deterministic subsetting; round robin can leave a 2x CPU spread; least-loaded and weighted round robin.
- **Ch. 21:** capacity in resources (CPU) not QPS; adaptive client-side throttling with K = 2 over a two-minute window; criticality levels; retry rules: up to three attempts per request, per-client retry budget of 10% (growth about 1.1x instead of about 3x), retry only at the layer above.
- **Ch. 22:** cascading failure = positive feedback; queue size around 50% of the thread pool or less; load shedding with HTTP 503; LIFO or CoDel; randomised exponential backoff with jitter; example server-wide budget 60 retries per minute; 3 retries at each of 3 layers gives 4^3 = 64 attempts; deadline propagation (30 s - 7 s = 23 s, then 19 s); N+2 example: 5,000 QPS per cluster, peak 19,000 QPS gives about six clusters; bimodal latency example gives an 80.4% error rate.
- **Ch. 23:** split brain case study; 2f + 1 replicas tolerate f failures; three replicas minimum, five recommended; six replicas can be worse than five (quorum four of six); FLP result; use proven consensus for leader election and locks; monitor leader existence and leader changes.

## 3. AWS Builders' Library facts we may restate
- **Load shedding** (Yanacek): reject work cheaply to keep goodput; test beyond the breaking point; bound queue age and depth; keep health checks top priority.
- **Avoiding fallback** (Gabrielson): retry, proactive retry, failover, fallback are different; fallback is hard to test and often makes outages worse; if essential, exercise it constantly. Historical account: a cache-failure fallback overloaded the database (his account, around 2001).
- **Idempotent APIs** (Featonby): a caller-chosen unique request id; record the id atomically with the mutation; a retry returns the same meaning as the first success; same id with different parameters is an error; the SDK reuses the id on retries.
- **Queue backlogs** (Yanacek): queue systems are bimodal; measure message age; spillover and backlog queues; time-to-live drops; dead-letter queues; shuffle-sharded queues. Examples: an hour outage needs double capacity for another hour; Little's law 100 msg/s x 100 ms is about 10 threads, a 10 s latency gives about 1,000.
- **Shuffle sharding** (MacCárthaigh): 8 workers, 2 per shard gives 28 combinations, 7 times better than 4 regular shards; Route 53: 2,048 virtual name servers, 4 per domain, about 730 billion combinations.
- **Caching** (Chhabra): cache addiction; on-box vs external; soft and hard TTL; negative caching; request coalescing; version cached formats.
- **Fairness** (Yanacek): token buckets, per-tenant quotas, 429 for rate exceeded (RFC 6585).

## 7. Diagrams (the owner's point: diagrams are very important in HLD)
What the system can draw today (read from `Diagram.jsx`, `diagramLayout.js`, `notes.validators.js`): three kinds, `flow` (2 to 8 boxes in a row or stacked), `layers` (2 to 8 stacked boxes) and `graph` (2 to 10 labelled boxes at percent positions with straight arrows, a 600 x 280 canvas), **at most 3 diagrams per section**, no box shapes, no groups, no numbered steps, no sequence view.
That is enough for a concept sketch but **not for system design**: a normal HLD figure has 10 to 15 parts (client, CDN, gateway, load balancer, services, cache, database, queue, workers, object store), shows database and queue shapes, groups parts by zone or data centre, and numbers the request path. A Raft election, a two-phase commit or a retry storm needs a *sequence* diagram (messages over time). Ten case studies at three diagrams each cannot show the main design plus a read path, a write path and a failure case.
**Proposed upgrade (owner to approve; see the plan):** one shared diagram component change that every subject gets:
1. `graph` up to 14 nodes on a taller canvas, with a node `shape` (box, database, queue, cache, client, cloud/external), optional `group` boxes (a labelled zone around several nodes), numbered edges (1, 2, 3 on the arrows) and a dashed edge style for async paths.
2. A new `sequence` kind: 2 to 5 actors, 3 to 12 messages in order (for Raft, 2PC, retries, cache-aside, OAuth-like flows).
3. The 3-per-section limit stays for existing subjects; HLD sections may have up to 6.
4. Same rules as before: plain data, caption mandatory, redrawn with the site colours in light and dark, readable at 375 px width (check by a browser screenshot), tests for the layout and for every new validation rule.
Diagrams in the notes are always our own drawings from the data; no figure from any paper or book is copied or traced.
