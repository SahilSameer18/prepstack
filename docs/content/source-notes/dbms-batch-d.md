### Introduction (chapter 1)
- Database applications: enterprise information, banking and finance, universities, airlines, telecommunications, web services, navigation systems. (1.2, 1.3)
- Why database systems exist. Early applications were built directly on file systems, which led to: data redundancy and inconsistency (the same data in several files and formats); difficulty accessing data (a new program for each new task); data isolation (many files and formats); integrity problems (rules such as "balance > 0" buried in program code and hard to change); atomicity of updates (a failure leaves partial updates, for example a fund transfer must complete or not happen at all); concurrent access (two people reading a balance of 100 and each withdrawing 50 at the same time can corrupt it); security problems (hard to give access to some data and not all). Database systems offer solutions to all of these. (1.4, 1.5)
- A data model is a collection of tools for describing data, relationships, meaning and constraints. Models named: relational, entity-relationship (mainly for design), object-based, semi-structured (XML), and older network and hierarchical models. (1.6)
- Relational model: all data stored in tables, with columns and rows; Ted Codd, Turing Award 1981. (1.7)
- Logical schema is the overall logical structure of the database (like a type in a program); physical schema is the overall physical structure; an instance is the content at a particular moment (like a variable's value). (1.10)
- Physical data independence: the ability to change the physical schema without changing the logical schema; applications depend on the logical schema. (1.11)
- DDL defines the schema; the DDL compiler stores table definitions in the data dictionary, which holds metadata (data about data): the schema, integrity constraints such as the primary key, and authorization. (1.12)
- DML accesses and updates data and is also called the query language; classes: pure (relational algebra, tuple and domain relational calculus) and commercial (SQL is the most widely used). Procedural DML says what data and how to get it; declarative (non-procedural) DML says only what data, and is usually easier to use. (1.13, 1.14)
- SQL is non-procedural; a query takes one or more tables and always returns a single table; SQL is not Turing-machine equivalent, so applications use a host language (C, Java, Python) with embedded SQL or an API such as ODBC or JDBC; SQL itself does not handle user input, display output or network communication. (1.15, 1.16)
- Database design: logical design (which attributes to record is a business decision; which relation schemas to have is a computer science decision) and physical design (physical layout). (1.17)
- A database system is partitioned into three functional components: the storage manager, the query processor and transaction management. (1.18)
- Storage manager: the interface between the low-level stored data and the application programs and queries; it interacts with the operating system's file manager and handles efficient storing, retrieving and updating. Components: authorization and integrity manager, transaction manager, file manager, buffer manager. Data structures it implements: data files, the data dictionary, and indices (which give pointers to data items with a particular value). (1.19, 1.20)
- Query processor: the DDL interpreter (records definitions in the data dictionary); the DML compiler (turns a query into an evaluation plan of low-level instructions, and performs query optimization, picking the lowest-cost plan among alternatives); the query evaluation engine (executes the plan). The steps are parsing and translation, optimization, evaluation. (1.21, 1.22)
- Transaction management: a transaction is a collection of operations that performs a single logical function; the component keeps the database consistent despite power failures, crashes and transaction failures; the concurrency-control manager controls how concurrent transactions interact. (1.23)
- Architectures: centralized, client-server, parallel (shared memory, shared disk, shared nothing) and distributed (geographical distribution, heterogeneous schemas and data). (1.24) Two-tier: the application runs at the client and calls the database at the server. Three-tier: the client is only a front end, talks to an application server, and the application server talks to the database. (1.25, 1.26)
- Users: naive users (use ready-made application programs), application programmers, sophisticated users (query language or analysis tools, no programs), specialized users (CAD, audio, video and similar). The database administrator's tasks: schema definition, storage structure and access method definition, schema and physical organization changes, granting authorization, routine maintenance, backups, free disk space, monitoring jobs that could degrade performance. (1.27, 1.28)
- History: tapes and punched cards in the 1950s and early 1960s; disks and the relational model (Codd) in the late 1960s and 1970s; SQL becomes the industry standard in the 1980s; data warehouses and web commerce in the 1990s; big data storage systems and "NoSQL" systems in the 2000s. (1.29 to 1.31)

### ER model (chapter 6)
- Design phases: understand the users' data needs; choose a data model and produce a conceptual schema; then logical design (the relation schemas) and physical design. The two pitfalls of a bad design are redundancy (repeated information that can become inconsistent) and incompleteness (some aspects cannot be modelled). Normalization (chapter 7) is the other approach to judging a design. (6.2 to 6.5)
- An entity is a distinguishable object; an entity set is a set of entities of the same type with the same properties, described by attributes; some attributes form a primary key that identifies each entity. In a diagram a rectangle is an entity set and the primary key is underlined. (6.7, 6.8)
- A relationship is an association among entities; a relationship set is a set of such associations; in a diagram a diamond is a relationship set, and a relationship set can carry its own attributes (the `advisor` relationship with a start date). (6.9 to 6.13)
- Roles: when the same entity set appears twice in a relationship (course and its prerequisite course), each side plays a role. (6.14)
- Degree: a binary relationship involves two entity sets (most do); a ternary one involves three (instructor, student, project); non-binary ones are rare. (6.15, 6.16)
- Attribute types: simple and composite (a name made of first, middle and last), single-valued and multivalued (phone numbers), derived (age computed from date of birth); each attribute has a domain of permitted values. (6.17, 6.18)
- Mapping cardinality for a binary relationship set: one to one, one to many, many to one, many to many; some entities may not be mapped at all. In a diagram a directed line means "one" and a plain line means "many". (6.20 to 6.26)
- Participation: total (every entity of the set takes part in at least one relationship; double line) or partial (some may not). A line can carry minimum and maximum cardinality `l..h`; a minimum of 1 means total, a maximum of 1 means at most one, `*` means no limit. (6.27, 6.28)
- Primary key of an entity set: attributes that distinguish entities; no two entities may have the same values for all attributes. (6.31)
- Primary key of a relationship set: the union of the primary keys of the participating entity sets, plus the relationship's own attributes if any; the choice depends on cardinality: many to many uses the union; one to many and many to one use the primary key of the "many" side; one to one can use either side's key. (6.32, 6.33)
- Weak entity set: an entity set whose entities cannot be identified by their own attributes; it depends on an identifying (owner) entity set through an identifying relationship and is identified by the owner's key plus extra attributes called a discriminator. Example: section is identified by course_id, sec_id, semester, year. In a diagram it is a double rectangle, the discriminator has a dashed underline, and the identifying relationship is a double diamond. A strong entity set is one that is not weak. (6.34 to 6.37)
- Redundant attributes: an attribute that repeats what a relationship already says (dept_name in student when there is a stud_dept relationship) should be removed from the entity, although it comes back when the diagram is turned into tables. (6.38)
- Converting to tables: a strong entity set becomes a table with the same attributes; a weak entity set becomes a table that includes the primary key columns of the identifying entity; composite attributes are flattened into one column per component; a multivalued attribute gets its own table made of the entity's primary key and the attribute (one row per value); a many-to-many relationship set becomes a table of the two primary keys plus its own attributes; a many-to-one or one-to-many relationship set that is total on the many side is represented by adding the one side's primary key as a column to the many side's table (for a partial many side, this can produce nulls); a one-to-one relationship can put the extra column on either side; the table for the relationship between a weak entity and its owner is redundant. (6.41 to 6.48)
- Specialization: a top-down design step where sub-groups of an entity set (instructor is a person) become lower-level entity sets that inherit the attributes and relationships of the higher-level set; shown by an ISA triangle; the groups can be overlapping or disjoint, and the constraint can be total or partial. Generalization is the same idea bottom-up. Two ways to build tables: a table for the higher-level entity plus a table per lower-level entity holding the higher-level key and local attributes (reading one entity needs two tables), or a table per entity set with all inherited attributes (some data may repeat for people in two groups). (6.50 to 6.56)

### Query processing and optimization (chapters 15 and 16)
- Query processing steps: parsing and translation (check syntax and relations, translate to relational algebra), optimization, evaluation. A relational algebra expression has many equivalent expressions, and each operation can be done by several algorithms; the annotated expression is an evaluation plan (for example use an index on salary, or scan the whole relation and discard rows). Optimization chooses the lowest-cost plan using statistics from the catalog such as the number of tuples. (15.3 to 15.6)
- The cost difference between plans can be enormous, "seconds versus days in some cases". Cost-based optimization: generate equivalent expressions with equivalence rules, annotate them to get plans, choose the cheapest by estimated cost; the estimates use statistics such as the number of tuples and the number of distinct values of an attribute, and cost formulas for each algorithm. (16.4, 16.5)
- Most databases support `explain <query>` to display the chosen plan with cost estimates; PostgreSQL also has `explain analyse`, which runs the query and shows actual runtime figures, and shows cost as `f..l` (cost of the first tuple and of all results). (16.6)
- Equivalent expressions give the same result on every legal database instance. Example rules: a selection can be pushed through a join when it involves only one side; joins are commutative and natural joins associative; selection distributes over union, intersection and difference. Pushing selections down means doing them as early as possible, which shrinks the relations to be joined. Join order matters: compute the join that gives a small intermediate result first (for example select the Music instructors first, then join with their courses). Outer joins do not follow all join rules (`select year=2017 (instructor left outer join teaches)` is not equivalent to the same selection over the inner join, and outer joins are not associative). (16.8 to 16.21)
- Join algorithms named in chapter 15: nested-loop join (compares every pair of rows; needs no index and works for any join condition; expensive), block nested-loop join, indexed nested-loop join, merge-join (both inputs sorted on the join key), hash-join. (15.24 to 15.30, 15.46 to 15.53) The textbook's nested-loop cost example: with 5,000 student rows in 100 blocks and 10,000 takes rows in 400 blocks, the worst-case nested loop with student as the outer relation needs 2,000,100 block transfers, and 500 if the smaller relation fits in memory.

### Partitioning and replication (chapter 21)
- Horizontal partitioning divides the tuples of a relation among nodes (this is what "partitioning" means by default); vertical partitioning splits the columns. (21.3)
- Techniques for n nodes: round robin (tuple i goes to node i mod n); hash partitioning (hash the partitioning attribute to 0..n-1); range partitioning (a partitioning vector such as [5, 11] sends value 2 to node 0, 8 to node 1 and 20 to node 2). (21.4, 21.6)
- Comparison: round robin balances scans but every query must reach all nodes; hash partitioning is good for point queries on the partitioning attribute (one node is enough) and for scans, but range queries must visit all nodes; range partitioning is good for point queries and, for range queries, only one to a few nodes need to be visited; but a range query that fetches many blocks still reads them from few nodes, wasting parallelism, which is an example of execution skew. Partitioning is not useful for small relations, which are better kept on one node or replicated on all. (21.8 to 21.11)
- Replication aims at availability despite failures; data is replicated on 2, often 3, nodes; the unit is typically a partition; requests to a failed node are routed to a replica. Replicas can be in the same data centre (machine failures, lower latency) or in different data centres (data-centre failures, lower latency for nearby users). (21.21, 21.22)
- Replicas must be kept consistent: a master (primary copy) scheme sends all updates to the master and then replicates them; the open question is who takes over if the master fails. Update protocols: two-phase commit (assumes all replicas are available), persistent messaging (replicas updated asynchronously after the transaction commits), eventual consistency (reads from replicas can be inconsistent), consensus protocols (replicas agree on which updates in what order, even without a master). (21.23, 21.24)
- Parallel indexing: a local index covers only local data; a global index covers all data and is itself partitioned across nodes; a global primary index is on the partitioning attribute, a global secondary index is on another attribute. (21.25)

## S7d. Wikipedia (read 10 Nov 2026; CC BY-SA 4.0, "additional terms may apply")

Pages: CAP theorem (edited 26 Oct 2026, read in full), Shard (database architecture) and Replication (computing) (edited 6 Nov and 13 Oct 2026; **only the verbatim parts are used**, the licence and dates for these two came from a machine summary), ACID (24 Oct 2026).

- CAP theorem: the statement is that a distributed data store can provide at most two of consistency, availability and partition tolerance. Consistency here: every read gets the most recent write or an error (the page says this differs from ACID consistency). Availability: every request to a non-failing node gets a response, without a guarantee that it is the latest data (the page says this differs from "high availability" in software architecture). Partition tolerance: the system keeps working despite arbitrary message loss or delay. During a partition you must choose: cancel the operation (keep consistency) or proceed (keep availability, risk inconsistency); with no partition, both can be had. Misunderstandings the page names: "two out of three" misleads, because designers only give up consistency or availability during a partition (Brewer, 2012); the page says no distributed system can avoid partitions, so partition tolerance is generally required; CAP consistency and availability are not the ACID or high-availability meanings. PACELC (2010) adds the trade-off between latency and consistency when there is no partition. The page says no NoSQL database should be classed as CA, lists Cassandra, CouchDB and ScyllaDB as AP and MongoDB and Redis as keeping consistency during partitions.
- Shard: a shard is a horizontal partition of rows, each possibly on its own server instance; some data (dimension tables) can be copied to every shard. Advantages listed: smaller tables and indexes, load spread across servers, queries can go to one shard when the split follows a real-world segment such as region. Disadvantages listed: more complex SQL, extra software that can fail, single points of failure, fail-over servers need to hold all shards, backups need coordination, schema changes are harder. Ways to split: manual grouping (by region) or a technique such as consistent hashing. The page cites advice that sharding should come after other optimizations. Implementations named: MongoDB, Vitess (MySQL), Spanner, Oracle.
- Replication: three approaches named: single-leader (the leader takes writes and logs them to replicas; replicas mostly serve reads and can be stale because of replication lag), multi-leader (any node accepts writes; useful across data centres; synchronous (eager) replication detects conflicts before commit, asynchronous (lazy) replication resolves them later by last-write-wins, application logic or merging) and leaderless (named, not described). Techniques: statement-based (problematic for non-deterministic statements), write-ahead log shipping, logical (row-based). A backup may not match the primary after a failure and some transactions could be lost. Synchronous replication waits for the remote write (no data loss, slower); asynchronous has lag and possible loss; semi-synchronous sits between. Replicated databases are constrained by CAP or PACELC.
- ACID: the page says ACID databases prioritize consistency over availability.

## S2d. PostgreSQL 18 documentation, chapter 26 (read 10 Nov 2026)

Pages: `high-availability.html` and `different-replication-solutions.html`. Version 18; no date; copyright 1996-2026 PostgreSQL Global Development Group; permissive licence (batch A S2).

- Servers that take writes are primary (master); standby (secondary) servers follow the primary. Writes must reach every server or reads from other servers become inconsistent (the synchronization problem). A warm standby cannot accept connections until promoted; a hot standby accepts read-only queries.
- Synchronous: a transaction is not committed until all servers commit it, so a failover loses no data and balanced servers agree. Asynchronous: some delay is allowed, so transactions may be lost on failover and reads may be slightly stale; used when synchronous would be too slow. The page says a fully synchronous solution over a slow network might cut performance by more than half, while an asynchronous one might have minimal impact.
- Solutions described: shared-disk failover, file system (block device) replication, write-ahead log shipping (warm or hot standby, synchronous or asynchronous, whole server only), logical replication (row changes per table, can go both ways), trigger-based primary-standby, SQL-based middleware, asynchronous and synchronous multimaster, data partitioning, parallel query across servers. The page says PostgreSQL does not itself offer synchronous multimaster.

## Differences between sources the notes must not hide

1. **CAP "consistency" is not ACID "consistency".** Wikipedia's CAP page says so; the textbook defines ACID consistency as keeping constraints true (batch B S1b).
2. **"Pick any 2 of 3" is misleading.** The CAP page says the real choice is between consistency and availability during a partition, and that partition tolerance cannot be dropped for a distributed system.
3. **Replication versus partitioning.** Replication copies the same data to several nodes for availability; partitioning (sharding) splits different data across nodes for capacity. The textbook (21.3, 21.21) and Wikipedia treat them separately; they are often combined (each partition replicated).
4. **Query optimization is the system's job.** The textbook describes the optimizer choosing the plan from statistics; a person does not rewrite queries by relational algebra rules, but `EXPLAIN` lets them see the choice (S1d 16.6, S2c 14.1, S8c 15.8.2).
