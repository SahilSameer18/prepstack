### Indexing (chapter 14)
- An index speeds up access to wanted data, like the author catalogue in a library. A search key is the attribute (or set) used to look records up. An index is a file of entries of the form (search key, pointer); index files are typically much smaller than the data file. Two basic kinds: ordered indices (keys stored sorted) and hash indices (keys spread over buckets by a hash function). (14.3)
- How to judge an index: which access types it supports efficiently (a specific value, or a range of values), access time, insertion time, deletion time, space overhead. (14.4)
- Clustering index (also called primary index): in a sequentially ordered file, the index whose search key gives the file's order; its key is usually, not always, the primary key. Secondary index (nonclustering): its key gives an order different from the file's. (14.5)
- Dense index: an entry for every search-key value. Sparse index: entries for only some values; it applies when the file is sorted on the key; to find K, find the entry with the largest key smaller than K and scan from there. Sparse uses less space and has less maintenance cost but is generally slower to locate a record. Secondary indices have to be dense. (14.6 to 14.10)
- Multilevel index: if an index does not fit in memory, build a sparse index over it (outer index over inner index), and so on. All levels must be updated on insert and delete. (14.11)
- Composite search key: for example (name, ID), sorted lexicographically; you can query on just `name` or on `(name, ID)`. (14.13)
- B+ tree properties: all paths from root to leaf have the same length; each non-root, non-leaf node has between n/2 and n children; a leaf holds between (n-1)/2 and n-1 values; a non-leaf root has at least 2 children. Leaves hold pointers to records and the last pointer goes to the next leaf in key order; non-leaf nodes form a multilevel sparse index on the leaves. Logically close blocks need not be physically close. (14.15 to 14.20)
- Lookup: start at the root, at each non-leaf node go to the child whose key range contains the value, until a leaf; then look for the key in the leaf. Range queries use the leaf order. (14.21, 14.22)
- Height is at most about log base n/2 of the number of keys. A node is usually one disk block (about 4 KB) and n is typically around 100. With 1,000,000 keys and n = 100, a lookup touches at most about 4 nodes; a balanced binary tree over the same keys touches about 20, and each node access can be a disk I/O (about 20 ms on the disks the slides assume). (14.23)
- Non-unique search keys: add a record identifier to make the key unique (widely used). With a clustering index the matching records are read sequentially; with a non-clustering index each record may cost one I/O. (14.24, 14.36)
- Insertion: find the leaf; if it has room, insert; otherwise split it and push the smallest key of the new node into the parent, splitting upwards if needed; the root may split and the tree grows by one level. Deletion: remove the entry; if the node is too empty, merge with a sibling if both fit in one node, otherwise redistribute entries between them; updates may cascade up; a root left with one child is removed. Cost of one insert or delete is proportional to the tree height; in practice splits and merges are rare. Average leaf fullness is about two thirds with random inserts and one half with sorted inserts. (14.25 to 14.35)
- B+ tree file organization: the leaves hold the records themselves, which keeps records clustered through inserts and deletes. A secondary index on such a file can store the key of the file instead of a record pointer, because records move when nodes split. (14.37 to 14.39)
- Indexing strings: variable fanout; prefix compression keeps just enough characters to separate subtrees. (14.40)
- Bulk loading: inserting entries one at a time costs at least one I/O each; sort first, then insert in order, or build the tree bottom-up; most systems have a bulk-load utility. (14.41)
- B-tree versus B+ tree: in a B-tree keys can appear in internal nodes without repeating in leaves (an example figure shows both). (14.42)
- Hashing: a hash function maps a search key to a bucket (usually a disk block); different keys can land in the same bucket, so the bucket is searched. In a hash index buckets hold entries with pointers; in a hash file organization buckets hold records. (14.46) Bucket overflow comes from too few buckets or skew (many equal keys or a poor hash function); it is handled with overflow chaining. (14.47, 14.48) Static hashing has a fixed number of buckets, so growth causes overflows and shrinkage wastes space; dynamic hashing (periodic rehashing, linear hashing, extendable hashing) changes the number of buckets. (14.50, 14.51)
- Ordered indices versus hashing: hashing is generally better for retrieving records with a given key value; if range queries are common, ordered indices are preferable. (14.52) The slide also says PostgreSQL supports hash indexes "but discourages use due to poor performance"; this is old advice, so **we do not repeat it** (see S2c below for what PostgreSQL 18 says).

### File organization (chapter 13)
- A database is stored as files; a file is a sequence of records; a record is a sequence of fields. (13.2)
- Ways to organize records in a file: heap (a record can go anywhere there is space), sequential (ordered by a search key), multitable clustering (records of several relations in the same file so related records share a block), B+ tree file organization (ordered even with inserts and deletes) and hashing (a hash of the key picks the block). (13.10)
- Heap file: records do not usually move; the system keeps a free-space map to find room. (13.11) Sequential file: good for processing the whole file in order; inserts that do not fit go to an overflow block and the file is reorganized from time to time. (13.12, 13.13)
- Multitable clustering is good for queries that join the clustered relations and bad for queries that read only one of them. (13.15)
- Table partitioning: a relation can be split into smaller stored relations (for example a transaction table into one per year); a query with a selection on the partitioning column needs only one partition; partitions can live on different storage devices. (13.16)
- The data dictionary (system catalog) stores metadata: relation and attribute names and types, views, constraints, statistics such as the number of tuples, how a relation is stored, and information about indices. (13.17)
- Blocks are the unit of storage allocation and transfer; the database tries to minimise block transfers between disk and memory; the buffer manager keeps copies of disk blocks in memory, and evicts a block (writing it back only if modified) when it needs room; plain LRU can be bad for some access patterns such as a nested-loop join. (13.19 to 13.22)

### SQL (chapters 3 and 4)
- Set operations union, intersect and except remove duplicates automatically; the `all` forms keep them. (3.27)
- Null: it means an unknown value or a value that does not exist. Arithmetic with null gives null (`5 + null`). `is null` and `is not null` test for it. A comparison with null, `5 < null`, `null = null`, `null <> null`, gives unknown. Boolean logic is extended: true and unknown = unknown; false and unknown = false; unknown and unknown = unknown; unknown or true = true; unknown or false = unknown. A WHERE predicate that evaluates to unknown is treated as false. (3.28, 3.29)
- Aggregate functions work on a multiset of values and return one value: avg, min, max, sum, count. `count(*)` counts the rows. (3.30, 3.31)
- A non-aggregated column in the select list must appear in the `group by` list; the slide shows `select dept_name, ID, avg(salary) ... group by dept_name` as an erroneous query. (3.33)
- `having` predicates are applied after groups are formed; `where` predicates before. (3.34)
- A subquery is a select-from-where nested in another query; it can be used in the from clause, the where clause (`B <operation> (subquery)`) or the select clause (a subquery that returns one value). (3.35) The `with` clause defines a temporary relation that exists only for that query. (3.43)
- Natural join matches on all common attribute names and keeps one copy of each. It is dangerous when unrelated columns share a name: the slide's example `student natural join takes natural join course` silently drops students who take courses outside their own department, because both `student` and `course` have `dept_name`. (4.4, 4.9)
- An outer join avoids loss of information: it computes the join and then adds the rows of one relation that match nothing in the other, filled with nulls. Three forms: left, right, full. Join condition decides which rows match; join type decides what happens to rows that match nothing. (4.10 to 4.16)
- A view is a virtual relation defined by a query; the definition saves the expression, and the expression is substituted into queries that use the view (view expansion). Views can hide columns from some users, and can be defined over other views. (4.19 to 4.23)

## S2c. PostgreSQL 18 documentation (read 10 Nov 2026)

Pages: `indexes-types.html` (11.2), `tutorial-join.html` (2.6), `tutorial-window.html` (3.5), `queries-table-expressions.html` (7.2: join types and 7.2.3 GROUP BY and HAVING), `functions-subquery.html` (9.24), `functions-comparison.html` (9.2), `queries-limit.html` (7.6), `queries-union.html` (7.4), `queries-with.html` (7.8 introduction), `using-explain.html` (14.1). Version 18; no dates on the pages; copyright 1996-2026 PostgreSQL Global Development Group; permissive licence (batch A S2).

- Index types: B-tree (the default for `CREATE INDEX`), Hash, GiST, SP-GiST, GIN, BRIN. B-tree handles equality and range queries on sortable data (`<`, `<=`, `=`, `>=`, `>`, also BETWEEN, IN, IS NULL, IS NOT NULL) and can return rows in sorted order; `LIKE` uses it only for a constant pattern anchored at the start such as `'foo%'`. Hash stores a 32-bit hash of the value and handles equality only. GIN is an inverted index for arrays and containment tests. BRIN stores a min and max per range of table blocks and works best when values follow the physical row order. (11.2) The page does not mention clustered versus secondary indexes.
- Join types: CROSS JOIN pairs every row (N x M rows); INNER JOIN pairs each row with its matches; LEFT OUTER JOIN adds each unmatched left row with NULLs for the right columns; RIGHT is the mirror; FULL adds the unmatched rows of both sides. INNER and OUTER are optional words; LEFT, RIGHT and FULL imply outer. `ON` takes any boolean condition; `USING` lists shared column names and merges them into one output column; NATURAL uses all shared names and is riskier than USING because a later schema change can add a matching name. A condition in ON is applied before the join and a condition in WHERE after it, which does not matter for inner joins but does for outer joins. (7.2.1.1)
- Join examples (2.6): a join of `weather` and `cities` on the city name drops a weather row with no matching city; `LEFT OUTER JOIN` keeps it with empty city columns; a self join with two aliases compares rows of one table (for example `w1.temp_lo < w2.temp_lo AND w1.temp_hi > w2.temp_hi`). The page says to qualify column names in join queries and prefers the explicit `JOIN ... ON` form to listing tables with a WHERE condition.
- GROUP BY and HAVING (7.2.3): the pipeline is FROM, then WHERE, then GROUP BY, then HAVING. GROUP BY merges rows with the same values in the listed columns into one group row; a column that is not in GROUP BY may be used only inside an aggregate (unless it is functionally dependent on the grouped columns, for example when the primary key is grouped). HAVING works like WHERE but filters groups after grouping and may use aggregates. An aggregate without GROUP BY gives one group row.
- Subquery expressions (9.24): EXISTS is true when the subquery returns at least one row; the select list does not matter (`SELECT 1` by convention). IN is true when an equal value is found, false when none is (also for an empty subquery), and null when the left value is null or nothing matched and the subquery contains a null. **NOT IN is true only if every right-hand row is different; it is null (not true) when nothing matched and a right-hand row is null, so a NULL in the subquery makes NOT IN return no rows.** `= ANY` is the same as IN and `<> ALL` the same as NOT IN.
- Comparison and NULL (9.2): any ordinary comparison with a null input is null (`7 = NULL` and `7 <> NULL` are null); test with `IS NULL`, `IS NOT NULL`; `IS DISTINCT FROM` and `IS NOT DISTINCT FROM` treat two nulls as equal; do not write `expression = NULL`.
- LIMIT and OFFSET (7.6): without ORDER BY the returned subset is unpredictable; use ORDER BY with a unique order; skipped OFFSET rows are still computed, so a large OFFSET can be slow.
- UNION, INTERSECT, EXCEPT (7.4): UNION removes duplicates unless UNION ALL; INTERSECT and EXCEPT too unless ALL; both queries need the same number of columns with compatible types; INTERSECT binds tighter than UNION and EXCEPT; a LIMIT after the last query applies to the whole union.
- WITH queries (7.8): a common table expression is a temporary named result that exists for one statement; it can wrap SELECT, INSERT, UPDATE, DELETE or MERGE.
- Window functions (3.5): a window function computes across related rows and keeps every input row; an aggregate would collapse them. Syntax: a function call followed by `OVER (PARTITION BY ... ORDER BY ...)`. Page examples on a 10-row `empsalary` table: `avg(salary) OVER (PARTITION BY depname)`, `row_number()` within a department by salary descending (ties get numbers in no guaranteed order), `sum(salary) OVER ()` for a whole-table total (47100 on every row), and a running total with `sum(salary) OVER (ORDER BY salary)` where tied salaries share a value. With ORDER BY in the window, the frame runs from the start of the partition to the current row and its ties; without it, the whole partition. Window functions are allowed only in SELECT and ORDER BY, not in WHERE, GROUP BY or HAVING; to filter on a window result, use a subquery.
- EXPLAIN (14.1): shows the plan the planner chose as a tree of nodes; each node shows start-up cost, total cost, estimated rows and row width; costs use arbitrary units where fetching one page sequentially is 1.0. Examples on a 10,000-row table: a full sequential scan has cost 0.00..445.00 (345 pages x 1.0 + 10,000 rows x 0.01); `WHERE unique1 = 42` uses an Index Scan with cost 0.29..8.30 and one row; `WHERE unique1 < 100` uses a Bitmap Index Scan under a Bitmap Heap Scan, cheaper than the sequential scan because not all pages are read.

## S8c. MySQL 8.4 Reference Manual (read 10 Nov 2026; "(c) 2026 Oracle", no reuse licence stated)

- Clustered and secondary indexes (17.6.2.1): every InnoDB table has a clustered index that stores the row data. It is the primary key if there is one (the manual advises defining one; if there is no natural key, add an auto-increment column). Without a primary key it is the first UNIQUE index whose columns are all NOT NULL; with neither, InnoDB makes a hidden index over a 6-byte row id, so rows are stored in insertion order. A lookup through the clustered index goes straight to the page with the row. Each secondary index record holds the primary key columns plus the indexed columns, and finding the full row means searching the clustered index with that key; a long primary key therefore makes secondary indexes larger.
- JOIN (15.2.13.2): the grammar lists `[INNER | CROSS] JOIN`, `STRAIGHT_JOIN`, `LEFT [OUTER] JOIN`, `RIGHT [OUTER] JOIN` and `NATURAL` joins; **FULL OUTER JOIN does not appear** (the page does not say outright that it is unsupported). INNER, CROSS and plain JOIN are equivalent in MySQL. A left row with no match gets NULLs, and the pattern `LEFT JOIN ... WHERE right.id IS NULL` finds left rows with no match. RIGHT JOIN is LEFT JOIN with the tables swapped; the manual recommends LEFT for portability.
- UNION (15.2.18): `UNION [ALL | DISTINCT]`. The page does not state what happens without ALL or DISTINCT and does not cover INTERSECT or EXCEPT, so we do not make claims about them for MySQL.
- GROUP BY handling (14.19.3): `ONLY_FULL_GROUP_BY` is on by default in 8.4: a non-aggregated select column must be in GROUP BY or functionally dependent on it, otherwise the query fails (error 1055); `ANY_VALUE()` is the workaround; MySQL lets HAVING use select-list aliases.
- EXPLAIN (15.8.2): shows the optimizer's plan for SELECT, DELETE, INSERT, REPLACE, UPDATE and TABLE statements, with formats TRADITIONAL, JSON and TREE.

Mistakes and loose statements found (do not repeat):
- The left join example in the 29-page file shows a result row `NULL | Monitor`, an order with no customer, as if a left join from Customers produced it. A left join from Customers keeps customers with no orders; an order with no customer would appear in a right or full join. The orders table in the same example is also inconsistent with the result (order 103 is Headphones).
- "Set operations are generally faster and less complex than joins" and "joins are more efficient than subqueries" are stated as general rules. Neither is supported by the manuals: the planner decides, and a subquery and an equivalent join can have the same plan. We do not repeat them.
- "HAVING ... is similar to WHERE i.e. applies some condition on rows" is loose. WHERE filters rows before grouping; HAVING filters groups after grouping (S1c 3.34, S2c 7.2.3).
- "Foreign key ... refers to the primary key in another table": it can reference any candidate key (batch A).
- `CHAR string (0-255)` and similar data-type ranges are MySQL specific, not general SQL.
- "FULL JOIN in MySQL: LEFT JOIN UNION RIGHT JOIN" is a workaround, not a feature; the UNION also removes duplicate rows, which can change the result when the data itself has duplicates.
- The "SELECT TOP / LIMIT / FETCH FIRST / ROWNUM" list in the DBMS notes is correct as a list of different databases' spellings (that source also says so); the PostgreSQL docs add that LIMIT without ORDER BY gives an unpredictable subset.

## S7c. Use The Index, Luke, and Wikipedia B+ tree (read 10 Nov 2026)

- Use The Index, Luke (Markus Winand; all rights reserved, no open licence shown; we cite and restate only): an index is a separate ordered copy of the indexed data that refers to the table, so it is redundant and must be updated on every write; it uses two structures, a doubly linked list of leaf nodes and a search tree above it. Leaf nodes are blocks of a few kilobytes linked to their neighbours and hold the key and a row pointer; the table itself is unsorted. The balanced search tree finds the right leaf: each branch entry holds the largest value of the leaf below it, layers are built until one root remains, all leaves are at the same distance from the root, and the depth grows only logarithmically with the fan-out (example: 4 entries per node and depth 3 give 64 entries; real indexes with millions of rows are depth 4 or 5, rarely 6). A B-tree is a balanced tree, not a binary tree. A multi-column index is one tree sorted by the first column, then the second within equal first values; a search on the second column alone cannot use that order (example: an index on (employee_id, subsidiary_id) does not help a filter on subsidiary_id only; reversing the columns turns the full scan into an index range scan); the index can be used through its leading columns; a full table scan can be the best plan when a large part of the table is read.
- Wikipedia B+ tree (CC BY-SA 4.0, only the verbatim part used): internal nodes hold keys only and leaves are all at the same depth; leaves are linked to the next leaf, which makes ordered and range scans simple (a B-tree cannot have such a list because not all keys are in leaves); the fan-out is typically on the order of 100 or more; search, insert and delete are O(log_b n) and a range query is O(log_b n + k).

## Differences between sources the notes must not hide

1. **Hash indexes.** The 2019 textbook slide discourages PostgreSQL hash indexes; the current PostgreSQL manual lists Hash as an index type for equality only. The notes teach "hash is for equality; B-tree handles equality and ranges" and do not repeat the old advice.
2. **FULL OUTER JOIN.** Standard SQL and PostgreSQL have it (S1c, S2c); MySQL 8.4's JOIN grammar does not list it (S8c).
3. **Grouping rules.** PostgreSQL and MySQL both allow a non-grouped column when it is functionally dependent on a grouped key (S2c, S8c); the textbook slide shows the strict older rule (S1c 3.33). MySQL also lets HAVING use a select alias (S8c).
4. **Clustered indexes.** Described for InnoDB in S8c; the PostgreSQL index page does not cover them, so the notes make no claim about PostgreSQL's clustered behaviour.
