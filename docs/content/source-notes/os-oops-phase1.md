## 4. The owner's two PDFs (Tier 2: topics and mistakes only)
Both are "Apni Kaksha" short notes. **They are copyrighted study notes: read for topic lists and mistakes, nothing is copied, and they are not cited as a source of facts.**
- **Operating System Notes.pdf** (12 pages, about 3,300 words). Topics: OS types (batch, multiprogramming, multitasking, time sharing, real time), process and PCB, scheduling terms, threads (user and kernel), scheduling algorithms (FCFS, SJF, SRTF, RR, priority, HRRN, MLQ, MLFQ), critical section and its three conditions, semaphore and mutex, deadlock (four conditions, three ways to handle it, Banker's), memory (overlays, swapping, fixed and variable partitions, first/best/worst fit, fragmentation, paging, segmentation), page fault, page replacement (FIFO, Belady's, optimal, LRU), disk scheduling (FCFS, SSTF, SCAN, C-SCAN, LOOK, C-LOOK), kernels (monolithic, micro), re-entrancy, demand paging, virtual memory, RAID, spooling, starvation and aging, thrashing.
  Page-fault examples **checked by script (`pf.py`)**: FIFO on 1,3,0,3,5,6 with 3 frames = 5 faults (matches); Belady string 3 2 1 0 3 2 4 3 2 1 0 4 gives 9 faults with 3 frames and 10 with 4 (matches); on 7 0 1 2 0 3 0 4 2 3 0 3 2 with 4 frames optimal = 6, LRU = 6, FIFO = 7. The owner's text lists the individual faults without giving the total.
  **Mistakes or loose wording found (to be avoided or flagged):** "Macro Kernel is a combination of micro and monolithic" (the usual term is hybrid kernel); "Demand paging specifies that if an area of memory is not being used it is swapped to disk" (that describes swapping; demand paging loads pages when first used); C-SCAN is described in a way that repeats SCAN; "RAID stores the same data redundantly to improve performance" (not true for every level; RAID 0 does not store copies); "Batch OS... time sharing... requires interaction" are simplified; "Virtual memory enables processes to execute outside of memory" is loose. The classification "ignore the problem: Windows and UNIX take this approach" must be checked against OSTEP before use.
- **Object Oriented Programming (1) (1).pdf** (16 pages, about 2,700 words). **It is a C++ note, not Java.** Topics: class, object, inheritance (five types), encapsulation, abstraction, polymorphism (overloading, overriding), constructors (default, parameterised, copy), destructor, `this`, friend function, aggregation, virtual function, pure virtual function, abstract class, namespaces, access specifiers, `delete`/`delete[]`, virtual inheritance, operator overloading.
  **Mistakes found:** overloading is said to be possible "on the basis of the return type" (wrong: the return type alone does not overload a function in C++ or Java); `student s = new student();` is shown as C++ syntax (it is Java/C# style; in C++ `new` returns a pointer); "an object created without `new` has null in the stack" (wrong for C++); `this` "can be used to declare indexers" (a C# feature); "data binding" is listed under abstraction (it is UI binding, not abstraction); the friend-function note contradicts itself. Topics here that our Java list leaves out on purpose: friend function, namespaces, virtual inheritance, operator overloading, destructors (Java has none; garbage collection and `finalize` are covered only to say that).

## 7. Man pages and kernel pages (read 12 Nov, man-pages 6.19)
| Page | Facts we may use [S] |
|---|---|
| `pthreads(7)` | Threads in one process share global memory (data and heap) and each has its own stack. Process-wide: PID, open files, signal dispositions, working directory. Thread-private: thread ID, signal mask, `errno`. LinuxThreads (old, unsupported since glibc 2.4, threads had separate PIDs) vs NPTL (modern, 1:1 model, futex-based, all threads share one PID). `getconf GNU_LIBPTHREAD_VERSION` tells which |
| `wait(2)` | A terminated child nobody waits for stays a **zombie** (the kernel keeps PID, exit status, a process-table slot). When a parent dies, its zombie children are adopted by init or the nearest subreaper, which reaps them. The page does not describe live orphans separately |
| `pipe(7)`, `pipe(2)` | A pipe is a one-way byte stream with a read end and a write end, no message boundaries. Read blocks on an empty pipe; write blocks on a full one (or fails with EAGAIN if non-blocking). Capacity 65,536 bytes (16 pages) since Linux 2.6.11 with 4 KiB pages; `PIPE_BUF` is 4096 on Linux. Reading returns end-of-file when all write ends are closed; writing with no read end raises SIGPIPE |
| `fork(2)` (man-pages 6.19, read 12 Nov) | The parent and the child run in separate memory spaces. Linux implements `fork()` with copy-on-write pages, so the only cost is duplicating the page tables and creating a task structure for the child. The page names copy-on-write but does not define it, so the definition (share the pages until one side writes, then copy that page) comes from OSTEP `vm-complete` and the slides |
| `execve(2)` | Replaces the program of the calling process (text, data, stack, heap); it does not create a new process; the PID and open files (unless close-on-exec) stay |
| `getpagesize(2)` | Returns the page size in bytes; says a program should not hard-code the size because some architectures support several. **The page does not give "4 KB" for x86-64 nor state the `sysconf` advice**, so a Linux page-size figure needs another source (pipe(7) mentions "4 KiB pages" only for the pipe-capacity rule) |
| Kernel `sched-design-CFS`, `sched-eevdf` | CFS merged in 2.6.23; each task has a virtual runtime and the smallest runs next (red-black tree). The CFS page says CFS is "making room for EEVDF". EEVDF = Earliest Eligible Virtual Deadline First (1995 paper); the kernel began moving to it in 6.6 (2024). **Still no page that says which is the default today** |

## 8. Java pages (read 12 Nov): dev.java and JLS SE 27

**JLS SE 27** [V unless marked]: 8.1.1.1 an abstract class cannot be instantiated; 8.1.1.2 a class cannot be both final and abstract; 8.4.1 and 15.12.4.5 argument values initialise new parameter variables (the JLS never writes "pass by value", so that phrase is our own explanation of this rule); 8.4.8.1 to 8.4.8.3 overriding rules (a static method cannot be overridden, it is hidden; return types may be covariant; access cannot be reduced; no new checked exceptions); 8.4.9 overloads are chosen at compile time by argument count and types, the return type does not take part (15.12.2); 8.8 constructors are never inherited or overridden; 8.8.7 a constructor without an explicit call starts with `super()`; 8.8.7.1 `this(...)` calls another constructor of the same class, recursion is an error, and after the superclass constructor returns, instance initialisers and field initialisers run in textual order; 8.8.9 the default constructor calls `super()`; 12.4 a class is initialised once, the superclass first, static initialisers in textual order; 15.12.4.4 dynamic lookup: start at the run-time class, use an overriding method there, else go up to the superclass, else search the superinterfaces preferring a default method; a null target throws `NullPointerException`. **[S] only:** 8.10 (records) and 12.5 (creating instances). Use 8.8.7.1 for construction order.
**`Object` API (SE 27)** [V]: `equals` is reflexive, symmetric, transitive, consistent and false for null; the default is reference identity; equal objects must have equal hash codes; unequal objects need not have different ones; override `hashCode` whenever `equals` is overridden.
