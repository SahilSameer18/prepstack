# PrepStack: repository audit and architecture review

Date: 14 November 2026. This is an audit, not a feature implementation. No application code, content, seeds, environment files or dependencies were changed. No staging, commit, push, production seed, deployment or paid AI call was performed.

## Verdict

PrepStack has a sound foundation for a focused interview-preparation product. Its best direction is the connected journey already described in the strategy PDFs: choose a job or goal, identify gaps, do realistic daily work, review weak areas, and eventually collect evidence that the learner can apply and explain a skill.

The current implementation has much of the learning library and diagnostic tooling, plus a substantial deterministic planning backend. It does not yet deliver that whole journey. My plan's public builder, daily screens and analyzer connection are still pending. Several reproducible planner defects should be fixed before those screens depend on the API.

Keep the React/Express/MongoDB architecture. The immediate constraints are correctness, trustworthy public claims, integration and learner validation. A framework rewrite, microservices or another large feature would not address those constraints.

- Reviewed the runtime architecture and critical flows across server startup, all controller areas, models, routes, validators, middleware, services, client routing, authentication, API services, state, major pages, content loading, diagrams, quizzes, SEO, seed and evaluation tooling.
- Examined the test organization and assertions around critical rules; ran both full suites, lint, production build and SEO checks. Wrote and ran separate diagnostic reproductions against the existing pure modules, client auth hook and an in-memory API stack. These reproductions are audit evidence, not newly installed regression tests.
- Inspected the homepage in a browser at desktop and 375 x 812. Signed-in browser verification was attempted, but the disposable MongoDB process stopped while the web process stayed up; protected-page interactions were not completed. This environment failure is not reported as an application defect.
- This is a repository-wide engineering review with deep review of critical paths. It is not a claim that every lesson sentence, Java example, external reference, lockfile entry or historical document was independently fact-checked. Content was structurally checked by the existing tests and sampled for editorial review. No external primary sources were re-fetched, no current dependency advisory audit was run, and there was no production, load, cross-browser, screen-reader or penetration test.
- Existing untracked `.claude/` files were left alone. Dependencies, generated build output, Git internals and secret environment-file contents are not part of the source inventory.

## What we are building

PrepStack is a free preparation workspace for placement candidates and job switchers. Today it brings together:

| Area | Implemented behavior | Current boundary |
|---|---|---|
| DSA | Five sheets, topic lists, external problem links, dated solved progress, IST streaks, private problem notes | Solves are self-reported; progress is stored per sheet; no coding judge or automatic LeetCode sync |
| CS notes | Five subjects, 64 sections, examples, interview questions, mistakes, quizzes and diagrams | Quizzes are local UI state; no general saved assessment/evidence model |
| Roadmaps | Nine tracks, 83 steps with goals, time ranges, resources, practice and project prompts | No independent saved roadmap-completion model |
| Resume and behavioral | Resume examples/checklist/PDF; 50 behavioral questions in 10 categories with STAR guidance | Advice and practice material; no verified story bank or interview assessment |
| Role Analyzer | Resume/JD diagnosis, checked evidence snippets, code-computed score, skill advice, questions, saved report and checklist | AI still chooses requirements and marks; score is an estimate, not a validated hiring probability |
| Projects | Stack/domain/level inputs, validated AI idea, saved history with pagination | An idea is not a built project, reviewed artifact or verified competency |
| My plan | Pure generator and adjustments; saved-plan API, preview/apply, item results, review ladder, weekly summary | No `/my-plan` client route, plan service or complete daily workflow yet |
| Accounts | Password/Google login, refresh rotation, device sessions, reset email, password change, cascading deletion | Cross-site secure cookies; deployment/browser behavior still needs real-host checks |

Measured sheet data: Blind 75 has 75 entries/75 distinct links; NeetCode has 150/150; Striver SDE 193/191; A2Z 446/444; Love Babbar 450/423. Repeated entries are not all necessarily mistakes, but entries and distinct problems must be named differently in counts. Notes: OS 11, DBMS 10, Networks 10, OOP 10, System Design 23.

The five-system strategy is a direction, not the shipped architecture: Job Intelligence is partly present in the Analyzer; Preparation has the most implementation; Skill Verification, Project-to-Job Alignment and Interview Readiness mostly remain proposals. The current skill catalog is a useful resource map. It is not yet a shared, per-user record of demonstrated skills. The owner's skipped story bank and other deferred decisions remain deferred.

## How the pieces work together

### Accounts and private requests

The client loads the current user into AuthContext. Axios sends cookies and, after an eligible 401, coordinates one refresh with queued requests. The server validates both the access token and the referenced active login session. Refresh tokens are stored as hashes and rotated atomically with a short grace period. Logout, session revocation, password changes and account deletion invalidate server sessions. Unique database indexes back account and progress identity.

### Learning content

Markdown is parsed into the shared notes shape. Stable section/topic IDs connect notes, roadmaps, sheet topics and analyzer references. The strict validator checks published-section structure, quiz shape and diagram references. Seed commands publish source content into MongoDB; the notes API reads the database. Internal-reference tests and generated-catalog sync tests reduce drift. Actual source-backed accuracy remains a separate editorial responsibility.

### DSA and notes

A sheet reads public sheet content and private progress. A toggle uses one MongoDB pipeline update. Progress dates support IST streaks; problem notes are private, account-saved and keyed by problem link across sheets. The client debounces whole-note replacement and imports older browser notes in batches.

### AI

Project generation and the Analyzer use a shared provider cascade with validation, time budgets, limited retries, circuit breakers and fallback. Controllers enforce user limits and one in-flight request per user in process memory. Resume contact details are reduced before sending the text; names and work history remain. Full resume text is not saved, while short report evidence snippets and the job description are saved. Scores are computed by code from AI-provided classifications; deterministic arithmetic does not make those classifications objectively correct.

### My plan

The generator receives content and settings explicitly. Dates, estimates, ordering, daily budgets, splitting and coverage are deterministic. The adjustment module handles results, review ladders, skips, moves, carry-over, lighter days and rebuild diffs. The controller adds ownership, persistence, concurrency guards on change application and DSA progress synchronization. Public preview returns coverage and only week one. The frontend still uses the older Analyzer Today card and report checklist.

## What is strong

1. Scheduling is plain code, separate from AI, persistence and the clock. This keeps the core affordable, explainable and testable.
2. Ownership filtering, database indexes, refresh races, deletion cascades and failure rollback receive meaningful testing, including replica-set paths.
3. Stable content IDs, validators, catalog regeneration and internal-link checks are a useful foundation for a connected curriculum.
4. The content process records sources, computed examples, review limits and missing outside readers. Those caveats should remain visible.
5. Shared UI states, color tokens, lazy routes and on-demand PDF loading already address several maintenance and performance concerns.
6. The product plan has unusually clear non-goals: free access, no new AI dependency for scheduling, one active plan and a deliberately calm Today screen.

## Confirmed findings

Severity: P1 means fix before relying on or promoting the affected flow; P2 means a material correctness or maintainability issue for the next relevant pass. These are distinct from future feature proposals.

### F1 — P1: planner item keys are not unique

Locations: `server/src/services/planGenerator.js:146`, `:172`, `:316`, `:376`; `server/src/services/planAdjust.js:237`; key-based helpers in `planAdjust.js` and `applyItemsUpdate` in `plan.controller.js`.

Reproduced with real data: frontend, backend, fullstack and java-spring role plans produce duplicate note keys. Notes are deduplicated within each roadmap step, but the key does not distinguish repeated occurrences across steps. A partially completed split problem can also collide with regenerated part numbering after rebuild; reproduced for Group Anagrams.

Impact: different displayed items share an identity. Helpers find the first key match, updates can affect the wrong occurrence, and completion/review grouping becomes ambiguous.

Recommendation: decide whether repeated learning is one deduplicated task or an intentional separate occurrence. Give occurrences and split parts stable, unique identities across rebuilds; validate uniqueness before saving. Add tests for every roadmap and partially completed split rebuilds. This does not require a new database architecture.

### F2 — P1: completing one split DSA part solves the whole problem

Locations: `server/src/controllers/plan.controller.js:379`, `:487`, and the read projection at `:82`.

Reproduction: generate a 12-week Blind 75 plan with half an hour per day. Tick part 1 of a two-part problem. The API returns 200, stores the sheet link as solved, and subsequently presents the unfinished second part as `solvedOnSheet: true`.

Impact: remaining work disappears from Today and the review ladder may never start through the normal workflow. The pure `markDone` helper waits for all parts, but the controller synchronizes the sheet on every part.

Recommendation: synchronize whole-problem progress only when all required parts are complete, and define matching untick behavior. Protect it with an API test spanning generation, both parts, GET, sheet progress and review creation.

### F3 — P1: Today can hide overdue work and due reviews

Location: `server/src/services/planAdjust.js:165`.

Reproduction: yesterday has unfinished work, a review is due today, today has no fresh scheduled item, and tomorrow has an item. Today selects tomorrow first; because `isToday` is false, it omits both the carry-over item and the due review.

Impact: students see future work while today's unfinished work is hidden. The same situation can occur after completing today's fresh items.

Recommendation: construct today's carry-over and review work before deciding that today is empty. Show the next date only when all eligible work for today is absent. Keep the owner's three-part Today UI rule unchanged.

### F4 — P1: logout can report success without revoking the session

Location: `client/src/hooks/useAuth.js:28` and `:46`.

Reproduced against the actual hook with a rejected logout service: `Promise.allSettled` resolves, the hook clears only the local user, and it reports no failure. The catch block is not reached for a rejected HTTP call.

Impact: the UI says the user is signed out while the server session and HttpOnly cookies may remain valid; reload can restore the session. Sign-out-all can make the same false claim about other devices.

Recommendation: inspect the request result separately from the animation delay and clearly distinguish local UI clearing from confirmed server revocation. Add client behavior tests for rejected logout and logout-all.

### F5 — P1: homepage promises exceed the implemented product

Locations: `client/src/components/homePage/Testimonial.jsx`, `MetricsStrip.jsx`, `EngineeringContrast.jsx`, `BentoGrid.jsx`, `FAQ.jsx`.

Verified examples:

- Four named company interview stories are presented as case studies, with first-person outcomes and numbers, but no supporting provenance was found in the repository. The text says "realistic", which does not clearly label individual stories as fictional. Obtain verifiable permission/evidence or clearly label/remove them; this audit cannot establish that the people or stories are real.
- Cross-sheet atomic syncing is advertised. The actual sheet toggle writes only `{ user, sheetSlug }`; the DSA normalization plan explicitly describes cross-sheet syncing as unfinished.
- "Zero lost checks" and "100% Atomic Progress" make guarantees broader than the implementation or tests establish.
- The page describes generated diagrams, Docker manifests, schema definitions and latency specifications. The current project output schema is a project idea with title, description, features, stack, level, estimated time and resume value. No corresponding CLI implementation was found for the displayed `prepstack spec` command.
- "Zero-knowledge" is used for ordinary token hashing. That is not the privacy architecture implemented by these files. The engineering notes already use more careful wording.

Impact: visitors may sign up expecting tools, outcomes or assurances that do not exist. This conflicts with the owner's source and plain-language rules.

Recommendation: describe observable learner benefits and current features. Clearly mark demonstrations and invented examples. Treat factual copy as part of release correctness. No need to redesign the whole page to fix its truthfulness.

### F6 — P2: weekly review disagrees with the main plan's completion view

Locations: `server/src/controllers/plan.controller.js:80` versus `:570` and `:631`.

The main plan overlays sheet solves as complete. Weekly review only uses stored item `doneAt`, and its on-track calculation also uses raw plan items. The reproduction showed two displayed completed split parts versus one weekly completion; independently, an external sheet solve follows only the overlay path.

Impact: different screens give conflicting progress and rebuild advice. The overlay also uses the current time instead of the original sheet solve date.

Recommendation: define one effective-progress projection using the stored solve timestamps and reuse it across plan reads, Today, weekly summaries and on-track calculations.

### F7 — P2: review results can be submitted before the review is due

Location: `server/src/services/planAdjust.js:64`.

Reproduced: an item due on 14 November accepts a passing review on 13 November and advances its ladder. The code checks whether a review exists, but not whether its due date has arrived. Repeated requests can advance future stages.

Recommendation: enforce the due date in the server helper, or explicitly define and document early practice as a different action. Add early/same-day repeated-request tests.

### F8 — P2: Google account-conflict handling loses its status code

Locations: `client/src/hooks/useAuth.js:84` and `client/src/pages/auth/Login.jsx:76`.

`handleGoogleLogin` replaces an Axios error with plain `Error`. Login then checks `error.response?.status === 409`, which is absent. The intended password-and-link flow cannot be selected from that error. Code-path finding; real Google sign-in was not run.

Recommendation: preserve structured error status/code across hooks, and test the existing-email 409 flow.

### F9 — P2: note autosave has no ordering or durable pending-write protection

Location: `client/src/hooks/useProblemNotes.js:20` to `:38` and `:69`.

Code-path risk: after the debounce fires, a newer edit can start another whole-note replacement while the earlier one is still pending. No per-link queue/version check prevents an older request from finishing last. `flush()` sends ordinary async requests without waiting; it does not guarantee delivery when the tab closes. The global saved status tracks timers rather than all in-flight operations.

Impact: a slow connection can overwrite newer text or show "saved" too early. No browser network-reordering reproduction was completed, so this is an identified missing guard, not a measured incident.

Recommendation: serialize saves per problem or use optimistic versions, retain recoverable pending text, and track in-flight writes. Test delayed/reordered saves, clear while saving, unmount and failed retry.

### F10 — P2: content imports have seed/environment side effects

Locations: `server/src/services/planData.js`, `server/src/seed/sheetSeeds/*.js:2`, `server/src/seed/seedConfig.js:6` to `:10`.

The planner loads sheet data through seed modules. Importing those modules also loads the seed connection helper, which calls dotenv against `server/.env` and can change process DNS. An initial diagnostic run emitted dotenv's environment-load message; no secret values were printed and no real database connection was made. Later diagnostic runs stubbed the seed helper before importing data. Some tests already use `sheetSeedData()` for this reason, but catalog imports do not uniformly enforce that isolation.

Impact: runtime data loading and supposedly isolated checks have hidden configuration side effects. This weakens the claim that all tests avoid loading the real environment.

Recommendation: move static sheet data into side-effect-free modules and keep dotenv/DNS/connection logic only in explicit seed entry points. Assert that importing catalogs does not load dotenv or alter DNS. No environment file was edited by this audit.

### F11 — P2: notes publishing can remove good data before replacement succeeds

Location: `server/src/seed/notesSeed.js:34` to `:41`.

The command validates source data, then deletes all notes and inserts replacements in separate operations. A database/network failure after deletion leaves the collection empty or incomplete; the catch logs the error without setting a failure exit status. This was identified in code, not executed against a real database.

Recommendation: use transactional replacement on the supported deployment, or validated per-subject upserts with a safe cleanup strategy; return a nonzero status on failure. Rehearse failure paths in an isolated database before the owner publishes content.

### F12 — P1: keyboard accessibility is uneven in shared controls

Locations: `client/src/components/ui/Accordion.jsx:15`, `client/src/components/homePage/FAQ.jsx:48`, `client/src/components/Navbar.jsx`, `client/src/pages/auth/Login.jsx`, `client/src/pages/Profile/components/DeleteAccountCard.jsx`.

Verified in source: shared accordion/FAQ controls remove the focus outline without a replacement; several expanding menus lack expanded/controlled state; the login password-visibility button has no accessible name; the delete-account overlay lacks dialog semantics and focus management. Other components, such as Behavioral questions and checklist labels, are more careful.

Impact: keyboard and screen-reader users can lose their place or miss control state. Focus visibility and control names relate to WCAG 2.4.7 and 4.1.2. This is not a complete WCAG certification or assistive-technology test.

Recommendation: standardize focus styles, named controls and reusable dialog behavior. Verify by keyboard, with automated component assertions and a screen reader before making accessibility claims.

## Specification and documentation gaps

These need reconciliation with the owner-approved plan rather than being silently treated as new decisions:

1. **Finished-plan history:** finished plans are retained and deletion exists, but no API route lists or reads history once the active plan has been replaced. `GET /` only finds active status. Expired plans return a `finished` flag but item helpers still find them by active database status. Define read/edit rules before building history screens.
2. **Second pass and spare time:** the generator returns an early-finish notice, but the promised general second-pass scheduling is not present. It also does not implement all the content-add/merge behavior described for later connections. Track those explicitly rather than assuming Phase 1/API completion covers them.
3. **Today specification:** decision 37 proposes a second "Pull tomorrow" button while sacred decision 33 allows one Start button. Keep the sacred constraint; the owner must resolve the placement of any extra action before implementation.
4. **Login return context:** ProtectedRoute drops the requested destination, and login navigates home. Phase 5 must deliberately preserve builder settings across login; current auth routing does not provide that behavior automatically.
5. **Counts and stale statements:** the status test row said 762/85 while the passing suites are 885/88; the handoff names a nonexistent router directory; TESTING retains an old "not built" list that includes startup tests despite their presence; several plan paragraphs mix done and next/waiting states. This audit updates its own status and verified counts but does not rewrite all historical records.
6. **Startup claim:** README says secret length is enforced, while `server.js` only warns on a secret shorter than 32 characters. Align documentation and policy in the next auth pass.
7. **Error reporting claim:** ErrorBoundary says "Our team has been notified", but its implementation only writes to the console. Use truthful copy until a reporting mechanism exists.

## Scale, security and reliability boundaries

- The modular monolith and MongoDB are appropriate for the current scope. No measured need for microservices, a graph database or a framework migration was found.
- Rate limits, in-flight AI locks, circuit breakers and several caches are process-local. Restart resets them, and multiple servers would not coordinate them. Follow the existing Redis plan when there is a measured deployment need; no Redis work was added by this audit.
- Daily AI usage is counted from saved records; deletion lowers the count, as documented. It is a saved-item allowance, not a permanent request/spend ledger. Do not describe it as an unbypassable global cost budget.
- The global AI provider quota can still be exhausted across users. Per-user success limits are useful but do not establish system-wide capacity.
- Transaction fallback is compensation/separate writes, not the same guarantee as a database transaction under process crash or concurrent failures. Production consistency guarantees should be stated for the actual database topology.
- Source catalogs and MongoDB content are separate deployment states. A generated plan can reference source content that has not yet been seeded into the API database. The owner's seed/deploy smoke check remains necessary.
- No production backup/restore drill, load report or operational error-alert delivery was verified. Existing health and access logs are useful starting points.
- CI remains deferred under the owner's current plan. This audit did not add it or override the decision against automated browser E2E.

## Product feedback and priorities

The strongest useful promise is: **"Tell PrepStack what you are preparing for; it gives you realistic work for today and helps you revisit what you struggle with."** The later evidence model can strengthen that promise once real use shows what needs verification.

Recommended sequence, for the owner's decision:

1. Correct or substantiate public claims and fix F1–F4 before building the planner screens on top of those contracts. Add focused regression tests that reproduce each failure; use mutation checks when implementing important rule changes.
2. Continue the approved My plan Phases 5–7: public preview, preserved login context, calm Today, results/reviews, previewed rebuild and Analyzer connection. Explicitly track the specification gaps above.
3. Have the owner seed/deploy safely and smoke-test actual data. Find the planned students, job switchers and outside readers now; completion of code and usefulness to learners are different milestones.
4. Measure first useful plan, first task completion, return to prep, review attempts, rebuild use and whether planned minutes feel realistic. Treat these as proposed metrics; no tracking was added.
5. After the pilot, extend stable skill IDs into task provenance and a small evidence record. Keep self-reported completion distinct from a quiz result, project artifact or demonstrated ability. Keep the Analyzer score diagnostic; do not present it as a job-readiness probability.
6. Revisit the normalized problem catalog and infrastructure work in the agreed build order. Preserve old links and progress when introducing permanent problem IDs. Leave the extension, DebugLab, extra AI coaching, leaderboards and paid-product ideas parked unless the owner changes their priority.

For a later frontend pass, `/impeccable harden` maps to the focus/menu/dialog and failure-state issues, followed by `/impeccable polish` after behavior and copy are correct. No redesign was performed.
